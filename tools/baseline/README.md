# Pinned Playnite baseline

Facts about the Playnite build this theme's ~68 near-verbatim copies were taken from.
Generated by [`../refresh_baseline.py`](../refresh_baseline.py), consumed by
[`../check_baseline.py`](../check_baseline.py) and [`../validate_theme.py`](../validate_theme.py).

Current pin: **Playnite 10.56.0** (see `VERSION`).

## Why this exists

`ThemeManager.ApplyTheme` merges the theme's copy of a file *over* Playnite's. A copy that
falls behind therefore overrides whatever Playnite ships next, silently and indefinitely,
because nobody re-reads a file that has not changed in the repo.

HYP-203 and HYP-204 were both that failure: a `PART_*` element quietly missing, taking its
functionality with it and logging nothing. HYP-202 was the mirror image — a core brush the
theme never redefined, so plugin windows rendered Playnite navy inside a near-black theme.

`ThemeApiVersion: 2.9.0` does not help here. `Themes.cs` gates it on major equality and
`<=`, so it is an API contract, not a file-content baseline.

## What is in here

Names only — file paths, `x:Key` names and `PART_*` names. **No Playnite markup is copied**,
so nothing third-party is redistributed and the whole fixture stays reviewable line by line.

| File | Contents |
|---|---|
| `VERSION` | the pinned Playnite version and the counts below |
| `default-theme-files.txt` | the 84 `.xaml` paths the default theme ships |
| `default-theme-keys.txt` | 177 `x:Key` names it defines |
| `external-keys.txt` | 1,177 names from `Templates/Themes` and `Localization` |
| `paint-keys.txt` | the 42 `Color`/`Brush` keys the theme must redefine or inherit Playnite's palette |
| `part-names.tsv` | `PART_*` names per default-theme file |
| `known-omissions.tsv` | `PART_*` names this theme drops **on purpose**, each with a reason |

`paint-keys.txt` is matched on the element's *type*, not the key's spelling.
`GridCornerDetailsPanel` is the reason: a name-pattern search misses any resource that does
not say what it is.

## Regenerating

After every Playnite upgrade, on a machine with Playnite installed:

```powershell
python tools/refresh_baseline.py --playnite "F:\Playnite"
```

Then **read the diff**. A noisy one is the signal this fixture exists to produce: it means
Playnite changed files the theme is shipping stale copies of. Work through the changes
before re-pinning.

`refresh_baseline.py` reads the version from `Playnite.dll` and takes the *highest* match,
not the first — the assembly also carries framework strings like `10.0.0` that sort earlier
and would silently pin a version that never existed.

## Editing `known-omissions.tsv`

`check_baseline.py` fails on any dropped `PART_*` not listed there, and also reports entries
that are no longer missing so the file cannot rot into a rubber stamp.

Adding a line is a decision, not a formality. Confirm the functionality is genuinely
replaced or genuinely unwanted first. The current entries are all one of two kinds:

- the theme keeps Playnite's `PART_Elem*` visibility wrapper but renders the contents itself
  instead of using `PART_Items*` (genres, tags, links, features)
- the theme does not surface that row at all (version, install directory, age ratings, and
  notes in the grid drawer only)

## What this cannot catch

CI has no Playnite install, so it compares `source/` against *this fixture*, never against
the Playnite on your disk. A Playnite release that adds a file or a key is invisible until
somebody regenerates. That is the trade that lets the check run on a Linux runner at all.
